Spend Envelopes — product & journeys
Product design · working name TBD

An agent shops the task. A human funds the envelope.
Consensus keeps it honest.

Before a task runs, the agent discovers real services, probes their prices, and returns a priced, reasoned plan. One approval funds a single-use envelope the agent physically cannot exceed — and every rejection teaches the system to ask less next time.

System

Three surfaces, one ledger

Three actors touch the product, and each gets the surface it would naturally reach for. The approval deliberately lives outside the agent's context: a prompt-injected agent must not be able to draw — or click — its own consent screen.

The agent · machine

MCP server

quote_task · submit_plan · await_approval · pay_and_call · report_drift. Framework-agnostic: anything that speaks MCP gets a budget. This is the reusable payment tooling.

The developer · terminal

Claude Code plugin

A SKILL that drafts and prices the plan inline, prints the approval link, and waits. The dev never leaves the flow; the decision still happens elsewhere.

The approver · any device

Next.js app

The plan at three depths, live execution feed, drift diffs, receipts, and the learning console. Magic-link auth; World Selfie Check as step-up on large plans.

Journey A · the demo backbone

The priced plan, and the drift

A developer asks their agent to vet three counterparty wallets before paying them. The agent shops a real market — every seller a stranger, discovered live — and what used to be a per-transaction popup becomes one priced, reasoned decision. When reality drifts from the plan, the agent hits a wall instead of the human's patience.

1

The dev asks; the agent shops a real market — and checks its own logic

In Claude Code, /plan-spend sends the goal. The agent searches the x402 Bazaar — Coinbase's public, keyless catalog — probes the candidates for live 402 quotes, then validates the plan against the goal and fixes what fails, up to 3 turns, before any human sees it.

Technically: quote_task → Bazaar semantic search (maxUsdPrice, curatedOnly filters — policy applied at discovery) → HTTP probes → each 402 response becomes a step with quoteSource: 'live-402' | 'estimate' and a one-line why. Every seller is a real third party; the probe is the reliability filter (a listing behind a bot wall never enters the plan). Self-check is bounded (≤3 turns), fixes logged — the human reviews a checked plan, not a first draft. An estimate is never dressed as a quote; reasoning is never more than a line.

3

Approval mints the envelope — approval is the money

No permission flag is set anywhere. An account is created and funded with exactly the ceiling; a sweep-back is scheduled for expiry; the plan and the approval land on the public record. Then the agent runs unattended.

On Hedera testnet, zero Solidity: HTS — envelope account funded to $1.20, key = 1-of-[2-of-2(agent, policy), treasury]: spends need both agent and policy signatures; the treasury alone can reclaim at any time. HSS — ScheduleCreate at approval: a full refund fires at 20:14 if the plan was abandoned; partial remainders are swept home by the control plane (scheduled transfers carry fixed amounts — "whatever remains" isn't schedulable, so we say so). HCS — plan hash + approval appended to the audit topic. On Base mainnet: the approve tap is itself the human's wallet signing the USDC transfer to the fresh plan wallet (gasless via EIP-3009; our relayer submits) — approval and funding are one act. Custody exists and is bounded: one plan's ceiling, one plan's lifetime, never the treasury. The purchases pay real sellers real money, every run.
Pre-flight re-verify: before the first cent moves, every quotable step is re-probed — a 402 probe is the current quote and costs nothing. A stale quote surfaces here, at zero sunk cost; what pre-flight can't cover is [est.] steps, which is exactly why they're labeled.
4

The drift — with the sunk cost on the table

Three steps are already paid when the sanctions screen — the one estimated step — asks $0.50 against its $0.10 estimate. The envelope could cover it, but a 5× step is a decision, not a rounding error: the co-signer refuses the per-step gate. The human gets a diff that answers three questions: what's already spent and what it bought, what changed, and what each exit costs.

Journey B · trust that compounds

Step-up, rejection, and the loop that closes

The second run shows what no threshold product has: memory. A big plan demands a face; a rejection carries a reason; the next plan arrives already shaped by it.

1

Above the line, the plan asks for a face

A $12 deep-audit plan — full portfolio history on all three wallets — crosses the $5 step-up threshold. Approval requires World Selfie Check — a liveness signal on a risky decision, not a login.

Technically: the agent was registered once in AgentBook (World ID proof, CAIP-122 challenge) — the fleet is provably human-backed. Selfie Check gates only high-value approvals: risk signal, which is exactly what the beta track rewards.
2

A rejection is the one answer worth mining

The dev rejects one step — "premium audit at $9/wallet isn't worth it, the $0.15 scan was fine" — typed as a price objection against that step's stated logic. Only rejections prompt for a reason. Approvals are mostly fatigue; 93% of permission prompts get approved. The signal lives in the no — and a typed no teaches the loop exactly which part of the reasoning failed.

3

The third plan arrives pre-shaped, and clears untouched

Next task: the agent's plan already uses the cheap tier; the console shows the insight that shaped it; the plan clears without interrupting anyone.

Enforcement

What actually holds the line

Graded honestly — the demo says which rung each guarantee lives on. Competitors' caps are database rows in a service that fails open. The envelope fails shut.

RungMechanismEnforcesGradeStatus
1 · Balance Envelope account funded to the ceiling, nothing more Total — you can't spend money that isn't there consensus ships now
2 · Expiry HSS scheduled full refund (abandoned case) · control-plane sweep for partial remainders · treasury co-key reclaims unilaterally Authority dies on time; funds always recoverable consensus (abandoned) key + ops (partial) ships now
3 · Co-sign Envelope key 1-of-[2-of-2(agent, policy), treasury]; policy signer refuses off-plan spends Allowlist + per-step caps — bypass is impossible, not forbidden; fails closed; treasury alone can reclaim key structure on-chain · policy off-chain ships now
4 · Plan-on-ledger ScheduleCreate per live-quoted step; agent releases via ScheduleSign; unused expire The exact approved transfers, and nothing else consensus roadmap slide
5 · Escrow Plan-authority contract releasing against the committed plan hash Full recipient restriction, Base included solidity · post-hackathon roadmap

Hedera testnet — the control plane

  • HTS — envelope accounts, 2-of-2 keys, the funded bound
  • HSS — expiry sweeps; the approve/manage-scheduled-actions UX
  • HCS — append-only plan → approval → receipt trail
  • Three native services, zero Solidity · HIP-1313 lane ≈ 10–12.5k TPS entity creation
  • Optional depth: labeled test seller on the Hedera rail (Blocky402 hosted testnet facilitator) — envelope ops already qualify; cut first if time runs short

Base mainnet — where the sellers are

  • Bazaar — keyless discovery: search, filters, curated flags (verified live)
  • x402 — all purchases from real sellers; a full plan runs $0.05–$0.50
  • USDC plan wallet; policy co-signer in the payment path
  • The Graph — subgraph indexes plan-wallet spend; console + loop read it live
  • 10,249 live mainnet endpoints · 882 providers (78,290-route census) · sepolia = CI fixtures only
Said out loud in the README: per-service policy logic is off-chain today (rung 3 makes it unbypassable, not on-chain); on Base the plan wallet's key is ours — custody bounded to one plan's ceiling and lifetime, never the treasury; the keeperless refund covers the abandoned-plan case, partial remainders are swept by us or reclaimed by the treasury key; every demo purchase pays a real third-party seller on Base mainnet — sepolia fixtures never appear in demo runs; demo drift is our own conservative estimate meeting a real seller's real ask; the learning history is real decisions from building the product with itself. Every other claim rides consensus.
