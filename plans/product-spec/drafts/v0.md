# Allowance — product spec v0

> **Status:** draft. Nothing here is agreed until it's promoted to `latest.md`.
> **One line:** Give your agents a budget, not your private key.

## 1. Idea

A control plane for agent spending.

A verified human funds one treasury and grants each agent a **capped allowance** — permission
to spend *from* the treasury, not funds of its own. The cap is recorded on the ledger, so an
overspend is refused by consensus rather than by our code.

One human, many agents, many services: one budget, one audit trail, one kill switch.

The agent never holds funds. There is nothing in its wallet to steal, leak, or lose, and
revoking it is a single transaction setting its allowance to zero.

## 2. Problem ↔ Solution

An AI agent that pays for anything today does it with a funded key in an environment variable:

```
PRIVATE_KEY=0x...                              # full control of a funded wallet
fetch = wrapFetchWithPayment(fetch, wallet)    # pays whatever the server asks
```

| Today | With Allowance |
|---|---|
| The wallet is the agent's. It can send anywhere | The agent holds permission to spend from a treasury it doesn't own |
| Pays the advertised price — `$10.00` as readily as `$0.01` | Per-call and per-period caps, evaluated before anything is signed |
| Five agents share one wallet; nobody can say who spent what | Every payment attributed to a named agent |
| Stopping an agent means rotating a key and redeploying | Set the allowance to zero — one transaction, immediate, unilateral |
| Limits enforced by a client library, if at all, and default permissive | Ceiling enforced by consensus — it holds even if our backend is down |

### The gap is documented, not hypothetical

- **OpenClaw #48140** asked for exactly this — trust levels, per-transaction and daily limits,
  velocity control, audit logs. Closed as not-planned.
- **MetaMask** and **thirdweb** have both published on agentic wallet risk; thirdweb proposed
  an Ethereum "Spend Mandate."
- Three papers on the x402 attack surface: arXiv **2605.30998** (*Free-Riding the Agentic
  Web*), **2604.11430** (*Hardening x402*), **2604.15367** (*SoK: Security of Autonomous LLM
  Agents in Agentic Commerce*), which proposes a layered defence close to §5 below.

### What it deliberately does not solve

- **Whether the spend was wise.** We enforce limits, not judgment.
- **Prompt injection itself.** We contain the blast radius; we don't prevent compromise.
- **Non-payment harm.** An agent can still delete data or send bad email. We govern money only.
- **Off-chain and fiat spending.** Card rails and SaaS subscriptions are outside the model.
- **Treasury custody.** If the operator's treasury key is compromised, everything is. We move
  the risk; we don't delete it.

## 3. Use cases

**A solo dev's research agent.** It buys data and API calls on a loop. Today the only control
is a cap in a client library. Here: a $20/day allowance, an allowlist of three data providers,
hard-fail on exceed. If a bad prompt sends it into a retry storm, it stops at $20.

**An agency running client-funded agents.** One agent per client, each on its own allowance
from a shared treasury. Attribution is per-agent by construction, so a client invoice is a
ledger query rather than a spreadsheet. A client offboards by setting one allowance to zero.

**A company's internal agent fleet.** Research, ops, and monitoring agents drawing on one
funded treasury across several teams. Finance sets the ceiling and reads the audit trail;
engineering ships agents without holding a funded key. Nobody needs to trust the other side's
process.

## 4. Product/market fit

### Who it's for

- **Primary — the agent operator.** Solo devs, dev shops, and teams running agents that spend.
  *"I want my agents to work autonomously without betting the treasury on it, and I want to
  know what they spent."*
- **Secondary — the person who signs off.** Finance, ops, or the tech lead who must approve
  agent spending at all. They don't use the agents; they need budget, attribution, and an audit
  trail, or the answer is no. This is why the product exists inside a company rather than as a
  hobby tool.
- **Not for** consumers, DeFi treasury management, or anyone who wants custodial convenience.

### The differentiation, in one sentence

*"They give the agent a funded wallet and enforce the limit in their own service. We give the
agent zero funds and let consensus enforce the cap — non-custodial, and it holds even if we go
offline."*

### The competitive honesty

**Skyfire**, **Payman**, and **Crossmint** ship spending controls for agent payments today.
We are not first to this category. All three are custodial by design — the platform holds the
funds and enforces limits in its own service — and that is the single axis we differ on.

> Read from each product's public documentation, July 2026. No claims here about competitors'
> funding, compliance certifications, or internals: unverified, and the argument doesn't need
> them. Re-verify the custodial characterisation before repeating it publicly — it's the one
> competitor claim this rests on.

### What would demonstrate fit, and hasn't

One operator saying they'd move real budget onto it. Evidence that non-custodial matters
enough to give up custodial convenience. Any signal on willingness to pay. None of this exists
yet — treat the above as a hypothesis with a good story.

## 5. Architecture

```
OPERATOR                      CONTROL PLANE                   AGENT           SERVICE
   │ verify (AgentKit)             │                            │                │
   ├──────────────────────────────►│ lookupHuman → humanId      │                │
   │ fund treasury                 │                            │                │
   │ set policy + allowance ──────►│ AccountAllowanceApprove ──►│ (permission)   │
   │                               │                            ├── request ────►│
   │                               │                            │◄── 402 ────────┤
   │                               │◄── policy hook ────────────┤                │
   │                               ├── allow / deny ───────────►│                │
   │                               │                            ├── pay from ───►│
   │                               │  log decision + tx → HCS   │   allowance    │
   │◄── live feed ─────────────────┤                            │                │
   │                               │  HSS: scheduled resets / top-ups            │
```

### Layers, hardest first

| Layer | Mechanism | Enforces |
|---|---|---|
| Ledger | Hedera `AccountAllowanceApproveTransaction` (HIP-336) | The hard ceiling. Overspend returns `SPENDER_DOES_NOT_HAVE_ALLOWANCE` from consensus |
| Policy | x402 V2 lifecycle hooks | Per-service caps, allowlists, period budgets — before a payment is signed |
| Identity | World AgentKit `lookupHuman` | Binds the fleet to one verified human. Revoke the human, revoke the fleet |
| Record | Hedera HCS topic, HSS scheduled transactions | Append-only decision/payment log; period resets with no keeper |
| Discovery | ENS subnames + ENSIP-26 text records | Publishes agent identity and current authority |

### Policy model

```ts
type Policy = {
  agentId: string
  totalAllowance: bigint        // enforced on-chain
  perCallMax: bigint            // enforced in hook
  periodBudget: { amount: bigint; window: 'day' | 'week' }
  allowedServices: string[]
  onExceed: 'block' | 'escalate'
  stepUpThreshold: bigint       // above this, require fresh liveness (Selfie Check)
}
```

### Traps, verified the hard way

- **The spender must be the transaction fee payer** when spending from an allowance, or you
  get `SPENDER_DOES_NOT_HAVE_ALLOWANCE` for entirely the wrong reason. The #1 integration trap.
- **ECDSA keys, not ED25519** — the EVM/ERC tools require it; a mismatch yields
  `INVALID_SIGNATURE` with no useful message.
- The package is **`@hiero-ledger/sdk`** (renamed from `@hashgraph/sdk`). Model memory gets
  this wrong.
- Decreasing an allowance means submitting the **new absolute amount**, not a delta.
- **Limits:** 100 allowances per owner account, 20 approvals per transaction. Real fleets shard
  across treasuries.

### Stack

Next.js + Tailwind console · Next.js route handlers + Postgres · LangGraph agent fleet ·
`@hiero-ledger/sdk` · `@worldcoin/agentkit` · x402 V2 client with hooks · deployed on Vercel.

**Fallback** if ledger allowances misbehave: enforce at a self-hosted x402 facilitator, where
we control `verify`/`settle` and can refuse to settle policy violations. Weaker guarantee,
still works.
